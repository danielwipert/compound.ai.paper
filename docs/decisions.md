# Decisions Log — Compound AI Architecture Benchmark

Append-only. Each entry: ID, date, decision, rationale, where it lives in the specs.
Decisions are made one gate at a time (logic-gates method) and are not reopened without a new entry superseding the old one.

| ID | Date | Decision | Why | Lives in |

| D1 | 2026-10-29 | Three experimental arms. **Arm B (tooled monolith)** — frontier model with JSON-schema structured output plus code-execution tool — is the **control**. Arm A (naive single-prompt monolith) is reported as a secondary arm. Arm C is the compound system. | A naive monolith is a straw man; beating it only proves Python is better at arithmetic. The claim that survives review is "compound ties the tooled monolith on accuracy and beats it on cost." Arm A is kept because it produces the "why this matters" figure. | product-spec §3; tech-spec TS-4 |
| D2 | 2026-10-29 | **Primary metrics are component-level**: field-mapping accuracy under schema drift, and extraction accuracy on unstructured carrier notes. **Halts are reported as coverage**, never folded into accuracy. End-to-end financial accuracy is a downstream metric. | The compound arm's financial math is Python, so 100% is tautological. Real risk lives in the small-model parsing nodes. A pipeline that halts on everything must not score 100%. | product-spec §4; tech-spec TS-7 |
| D3 | 2026-10-29 | **Staged scale.** Pilot: 100 rows × 1 drift level (15%) × 5 seeds. Full matrix: 500 rows × 3 drift levels (5 / 15 / 30%) × 5 seeds. Only the full matrix goes in the paper. | 100 rows at one noise level gives overlapping confidence intervals and no degradation curve. The pilot validates the build cheaply; the full run produces defensible statistics. | product-spec §5; tech-spec TS-10 |
| D4 | 2026-10-29 | **All compound nodes are hosted** (gateway: Hopscotch AI or OpenRouter). No local inference, no Docker. Each node has a declared fallback model; all calls use retry-with-backoff. | Author preference for cloud-only operation. Consequence: title/objective language shifts from "localized SLMs" to "small open-weight models." Fallbacks and backoff protect the 7,500-row full run from free-tier throttling. | product-spec §3.3; tech-spec TS-6 |
| D5 | 2026-10-29 | **Compound-arm cost is reported in two columns**: actual spend (free tiers, near $0) and list-price equivalent (same open-weight models at paid hosted rates). | "Free tiers aren't a production cost model" is a one-line rebuttal; the list-price column pre-empts it. Both columns still beat the monolith by a wide margin. | product-spec §4; tech-spec TS-7.6 |
| D6 | 2026-10-29 | **Pre-registration.** `docs/HYPOTHESES.md` (predicted direction per metric, not magnitude) and the analysis script are committed and git-tagged before the pilot runs. | Converts the original spec's pre-stated outcomes ("100% vs 85–92%") from advocacy into testable predictions. Matches Chorus spec-first discipline. | product-spec §6; tech-spec TS-9 |
| D7 | 2026-10-29 | **Monolith models**: Claude Sonnet 5.5 plus OpenAI's current mid-tier equivalent. Exact OpenAI model ID locked at build time from the OpenRouter feed. | Mid-tier flagships are what enterprises deploy at volume, so the cost comparison is realistic. Fits budget; Claude side covered by Max plan API credits. | product-spec §3.1; tech-spec TS-6.1 |
| D8 | 2026-10-29 | **Publication**: arXiv preprint (cs.AI or cs.SE); Zenodo DOI as fallback if no endorsement is secured by the time results are in. | D12 | 2026-10-30 | **Financial rounding (refines TS-7.4).** Money fields (`cost_basis`) are rounded to 2 decimal places and ratio fields (`profit_ratio_recomputed`, `profit_ratio_delta`) to 4, in `src/finance.py`. An arm's value matches ground truth if it is within half a unit of the last decimal: ±0.005 for money, ±0.00005 for ratios. Integer and enum fields (`delay_days`, `risk_class`) stay exact match. D10 and D11 remain reserved for model IDs and the prereg tag. | DataCo stores money with float noise (e.g. `-249.0899963`). With the original 1e-6 tolerance, a monolith answering `576.84` would be scored wrong against `576.8399963`, unfairly favouring Arm C, whose bus shares code with ground truth. | tech-spec TS-2.4, TS-7.4; `src/finance.py` |
| D13 | 2026-10-31 | **Keep 16 columns and the TS-2.4 formulas as written.** `profit_ratio_recomputed = benefit_per_order / sales`. `profit_ratio_delta` is reported as the gap between that and DataCo's stored ratio, which DataCo computes from post-discount `Order Item Total`; the paper says so in one sentence and does not call it a reconciliation check. OQ-2 (which field headlines) stays open. | Build-time finding: DataCo's `Order Item Profit Ratio` matches `Benefit / Order Item Total` in 96% of rows vs 18% for `Benefit / Sales`. Adding a 17th column would change TS-2.2 and the TS-3.2 drift counts for little gain; all arms are scored against the same formula, so fairness is unaffected. | tech-spec TS-2.4 |
| D14 | 2026-10-31 | **Stratum S3 redefined (TS-2.3).** Old rule `late_delivery_risk == 1 AND delivery_status != 'Late delivery'` matches zero rows. New rule: `delay_days > 0 AND late_delivery_risk == 0` (the risk flag says on time, the shipping days say late). Shares unchanged. Also fixed: the 500 rows are ordered in 5 blocks of 100, each block with the exact stratum shares, so the pilot's "first 100 rows" is itself stratified. | Build-time finding: in DataCo `late_delivery_risk == 1` exactly when `delivery_status == 'Late delivery'`. The new rule keeps S3's intent, a row whose label contradicts the facts. All such rows are cancelled shipments. | tech-spec TS-2.3; `src/golden.py` |
| D15 | 2026-10-31 | **Schema drift build locks (TS-3.2).** Renamed headers per level = `round(level × 16)` → 1 / 2 / 5. Variant seeds are `1–5` (`config/experiment.yaml`); each variant's generator is seeded with `[seed, level in percent]` so levels are independent. Variant folders are `data/noised/{05,15,30}/{1..5}/`. Rename pool: 6 alternates per renamable field (2 per style), all unique even ignoring case and punctuation. `header_map.json` holds both `renamed` (scored, TS-7.1) and the full 16-header `header_map` (un-renamed sanity check). | Resolves the TS-3.2 `BUILD` items with the spec's recommended rounding. Independent per-level draws avoid the 5% header always being one of the 30% headers. | tech-spec TS-3.2; `src/noise/` |
| D16 | 2026-10-31 | **Carrier-note build locks (TS-3.3).** (a) Notes depend on the **seed only**, not the drift level: every level of a seed has identical `carrier_notes` and `delay_facts`, so comparisons across drift levels change only the headers. (b) Numbers in notes agree with the row: `{days}` is the row's real `delay_days`; `{hours}` is drawn so it rounds up to `delay_days` (e.g. 25–48 h for 2 days). (c) 30 delay templates (all 8 causes; 2 with a secondary cause; 3 two-fact templates that split the delay, used only when `delay_days >= 2`) and 5 benign templates. (d) A template's facts may only state what its text shows (tested). (e) `delay_facts.jsonl` also records `template_id` for per-template error analysis; arms never see it. (f) Facts are in `facts:` lists so one note can state several facts. | Holding notes fixed across levels isolates the header-drift effect in the degradation curve (TS-8.3). Consistent numbers stop notes from contradicting the row, which would make extraction ground truth ambiguous. | tech-spec TS-3.3; `src/noise/`; `src/contracts.py` |
| D17 | 2026-10-31 | **Contracts and few-shot examples (TS-4.1, TS-4.2, TS-5.4).** (a) `ExceptionRecord`: on `HALT` only `order_item_id`, `status`, `halt_reason` are required; on `OK` all answer fields are required and `halt_reason` must be empty. (b) FactList key order is fixed in `src/facts.py`: F1–F15 canonical row fields (TS-2.2 order, minus `order_item_id`), F16–F20 derived fields, then each delay fact's non-empty fields as `delay_fact_N.<name>`; the FactList is frozen and its digest is checked on load. (c) 3 few-shot examples from DataCo rows whose `order_id` is not in the golden set (seed `[20261029, 2]`): LATE with one fact, LOSS_MAKING shipped early with a benign note, SEVERE_LATE with two facts in mixed units. (d) **No leakage:** few-shot header names are not in the rename pool and few-shot notes match no note template (both tested). (e) A report number counts as grounded if a FactList value rounded to the same decimals equals it (e.g. `129.99` ↔ `129.9900055`). | Few-shot examples built from the rename pool or templates would hand every arm answers for test rows, inflating accuracy. Fixing the key order now lets the few-shot reports cite real keys that the Arm C bus will reproduce. | tech-spec TS-4.1, TS-4.2, TS-5.4; `src/contracts.py`, `src/facts.py`, `data/fewshot/` |
